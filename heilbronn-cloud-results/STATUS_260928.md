### 01:05 — Correction: solver round-off is larger than first reported

- Earlier this session I reported "round-off at most 7.9×10⁻⁷". That figure is the solver's value minus the known optimum. The quantity that matters is the solver's value minus the exact value of its own points, and it is larger:
  - n = 7: up to 1.20×10⁻⁶;
  - n = 8: up to 1.09×10⁻⁶;
  - n = 9 on near-optimal sets: up to **1.82×10⁻⁶** (`split31_C/result_boundary_5.json`: 0.0269887164 against exact 0.0269868953);
  - n = 9 on one degenerate set with exact value 0: 6.56×10⁻⁶ (`cc31/47739da404/result_boundary_12.json`).
- Consequence: if the solver finds a set close to Cantrell's with a similar excess, its value would pass 0.0274248 (= target / (1 + 5×10⁻⁵)). The part could then stop as OPTIMAL with its bound still above the target (review finding 3), and splitting would not help.
- This has not happened in any run so far: 0 results are OPTIMAL but not PROVED, and the largest value above 43/1568 is 4.7×10⁻⁷.
- Option for the user to decide: tighter Gurobi tolerances (FeasibilityTol and IntFeasTol 10⁻⁹) in `gurobi.env` for the refinement of parts 0, 29, 30 and 31. This is a solver setting, not mathematics; it may slow the solver and is untested here.
- Soundness is unaffected: PROVED decisions use the solver's upper bound, and none of the 1,044 PROVED results has a bound above the target.
